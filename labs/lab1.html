ГАЙД ПО МОДУЛЮ М2: Контейнеризация TodoApp

Цель модуля: Упаковать наше приложение и базу данных (PostgreSQL) в Docker. Итогом работы должна стать инфраструктура, которая запускается одной командой: docker compose up --build.

ОТЛИЧИЕ ЭТОЙ РАБОТЫ: Мы не даем готовый код (кроме сложных платформенных особенностей). Ваша задача — понять логику работы инструментов, искать нужные команды в документации и осознанно применять их.

ШАГ 1: СОЗДАНИЕ DOCKERFILE (МНОГОЭТАПНАЯ СБОРКА)

Dockerfile — это инструкция по сборке образа вашего приложения (бэкенда). Мы будем использовать паттерн Multi-stage build (многоэтапная сборка).

Зачем это нужно? Для сборки кода нужен тяжелый .NET SDK (около 800 МБ). Но для работы готового приложения нужен только легкий .NET Runtime (около 200 МБ). Мы скомпилируем код в тяжелом образе, а готовый результат скопируем в чистый и легкий образ.

Этап 1.1: Builder (Сборка)

Начните Dockerfile с официального образа .NET SDK, назовите этот этап AS builder.

  1. Кэширование слоев: Сначала скопируйте Directory.Packages.props и только файлы проектов (.csproj) с сохранением структуры папок. Выполните dotnet restore.
    Почему так? Если вы измените строчку кода, Docker не будет заново качать пакеты из интернета, так как кэш файлов .csproj не изменился.
  2. Компиляция: Скопируйте остальной код (src/) и выполните публикацию проекта (ищите команду dotnet publish -c Release). Укажите флаг --no-restore.
  3. Бандл миграций: В проекте уже есть готовый скрипт scripts/make-migration-bundle.sh. Скопируйте его в контейнер и запустите.
    Важная подсказка: Чтобы утилита dotnet ef заработала в Linux, выполните следующие команды перед запуском скрипта: 
    RUN dotnet tool install --global dotnet-ef
ENV PATH="$PATH:/root/.dotnet/tools"
  4. Права доступа: Выполните chmod +x для бандла миграций и ваших скриптов, чтобы Linux разрешил их запуск.

🔎 Что гуглить: Docker layer caching dotnet restore

Этап 1.2: Runtime (Запуск)

Начните второй этап с образа .NET ASP.NET Runtime, найдите его правильный тег в интернете.

  1. Используйте команду COPY --from=builder, чтобы перенести в новый образ только три вещи: папку с опубликованным приложением, файл EfCoreMigrationsBundle и скрипт запуска (о нем в Шаге 2).
  2. Укажите порт (EXPOSE), например, 8080.
  3. Укажите ENTRYPOINT для запуска вашего скрипта (например, ENTRYPOINT ["/bin/sh", "./apply-migrations.sh"]).

ШАГ 2: СКРИПТ ЗАПУСКА (ENTRYPOINT)

Контейнер живет, пока работает его главный процесс. Нам нужно, чтобы при старте контейнер сначала обновил БД, а потом запустил само приложение.

  1. Создайте файл scripts/apply-migrations.sh.
  2. Напишите bash-скрипт, который сначала запускает ./EfCoreMigrationsBundle.
  3. Затем запускает приложение: exec dotnet TodoApp.Web.dll.
    (Команда exec нужна, чтобы передать приложению контроль над процессом и оно могло правильно получать сигналы остановки от Docker).

ШАГ 3: НАСТРОЙКА DOCKER COMPOSE (ОРКЕСТРАЦИЯ)

Приложению нужна база данных PostgreSQL. Писать длинные команды для связывания двух контейнеров вручную неудобно. Мы опишем нашу инфраструктуру в файле docker-compose.yml.

Этап 3.1: Безопасность и файл .env

Хардкодить пароли в коде — грубое нарушение безопасности. Docker Compose умеет читать переменные из файла .env.

  1. Создайте в корне проекта файл .env. Добавьте его в .gitignore
  2. Добавьте туда: DB_USER=postgres, DB_PASSWORD=secret, DB_NAME=todo_db.

Этап 3.2: Сервис базы данных (db)

Создайте файл docker-compose.yml. Внутри блока services: опишите первый сервис — базу данных. Назовите его db.

  1. Образ: Найдите на Docker Hub официальный образ PostgreSQL (например, postgres:15-alpine).
  2. Переменные (environment): База данных должна знать, какой логин/пароль создать при первом запуске. Передайте в environment системные переменные Postgres, подставив в них значения из вашего .env файла (например, POSTGRES_USER: ${DB_USER}).
    🔎 Что гуглить: Postgres Docker environment variables
  3. Сохранение данных (volumes): При удалении контейнера данные исчезают. Примонтируйте внутреннюю папку Postgres (/var/lib/postgresql/data) к именованному тому (например, postgres_data).
    🔎 Что гуглить: Docker compose named volumes example
  4. Проверка здоровья (healthcheck): База запускается несколько секунд. Добавьте проверку здоровья, чтобы бэкенд знал, когда база реально готова. Команда для проверки внутри контейнера Postgres: pg_isready -U ${DB_USER} -d ${DB_NAME}.
    🔎 Что гуглить: Docker compose postgres healthcheck pg_isready

Этап 3.3: Сервис бэкенда (backend)

Опишите второй сервис под названием backend (или api).

  1. Сборка (build): Укажите Docker-у собирать образ из текущей папки (build: .), где лежит ваш Dockerfile.
  2. Порты (ports): Пробросьте порт из контейнера (8080) на ваш локальный компьютер (например, 80:8080).
  3. Строка подключения (САМАЯ ЧАСТАЯ ОШИБКА): В appsettings.json вы писали Host=localhost. В Docker так делать нельзя! Для контейнера backend слово localhost — это он сам, а не база данных. Сетевой адрес базы данных — это имя ее сервиса в compose (т.е. db).
    Как решить: Задайте в блоке environment переменную ConnectionStrings__DefaultConnection (два подчеркивания заменяют двоеточие). Соберите строку подключения, используя Host=db и переменные из вашего файла .env (${DB_USER}, ${DB_PASSWORD} и т.д.).
    🔎 Что гуглить: ASP.NET Core environment variables connection string
  4. Зависимости (depends_on): Укажите, что backend зависит от db. Обязательно добавьте условие (condition: service_healthy), чтобы бэкенд начал запуск (и накатывание миграций) только тогда, когда db пройдет свой healthcheck.

ШАГ 4: ЗАПУСК И ПРОВЕРКА

Откройте терминал в корне проекта и выполните команду сборки и запуска. 

docker compose up --build
Как проверить результат: Дождитесь, пока в консоли появятся логи об успешном применении миграций и старте сервера. Откройте браузер и перейдите на http://localhost/swagger (или тот порт, который вы указали в настройках).

🔥 СЕКРЕТНЫЙ БОСС: ОТЛАДКА ЧАСТЫХ ОШИБОК

Если вы всё сделали правильно, но контейнер бэкенда моментально падает, внимательно изучите логи.

🔴 Ошибка в логах: exec format error или syntax error: unexpected end of file.

Причина (Невидимый враг): Контейнеры работают на Linux. В Linux окончание строк — это символ LF (\n). Если вы создали файл apply-migrations.sh в Windows, он сохранился с окончанием CRLF (\r\n). Linux "спотыкается" о невидимый символ \r и падает.

Как решить навсегда:

  1. Создайте файл .editorconfig в корне проекта, чтобы IDE создавала файлы правильно: 
    root = true
[*]
end_of_line = lf
insert_final_newline = true
  2. Создайте файл .gitattributes, чтобы Git всегда скачивал файлы в LF: 
    * text eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
  3. Важно: Выполните в терминале команды, которые заставят Git найти старые сломанные файлы и автоматически заменить в них CRLF на LF: 
    git add --renormalize .
git commit -m "Normalize line endings to LF"
  4. Пересоберите проект: docker compose build --no-cache.

🔴 Ошибка: Connection Refused при попытке подключения к БД.

Причина: Ваш бэкенд не видит базу.

Решение: Проверьте docker-compose.yml. Убедитесь, что:

  1. Вы передали правильную переменную ConnectionStrings__DefaultConnection.
  2. В строке подключения написано Host=db (или то имя, которое вы дали сервису БД).
  3. Переменные в .env полностью совпадают с теми, что требует образ Postgres.
