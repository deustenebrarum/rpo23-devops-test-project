ГАЙД ПО МОДУЛЮ М3.2: Перенос чувствительных данных в GitHub Secrets

Цель работы: Научиться безопасно управлять паролями, ключами доступа и токенами (чувствительными данными). Вы удалите все секреты из исходного кода репозитория и настроите их безопасную передачу через GitHub Secrets в ваш CI/CD пайплайн (GitHub Actions).

ПОЧЕМУ ЭТО КРИТИЧЕСКИ ВАЖНО? Боты-сканеры (хакерские скрипты) просматривают публичные репозитории GitHub 24/7. Если вы случайно закоммитите файл с реальным паролем от базы данных или секретным ключом JWT, он будет скомпрометирован за несколько секунд. Пароли никогда не должны храниться в коде.

ШАГ 1: АУДИТ БЕЗОПАСНОСТИ РЕПОЗИТОРИЯ

Перед тем как использовать GitHub Secrets, нужно убедиться, что паролей больше нет в самом коде.

  1. Проверьте файл docker-compose.yml. Если там жестко прописаны пароли (например, POSTGRES_PASSWORD: mysecret), замените их на переменные: POSTGRES_PASSWORD: ${DB_PASSWORD}.
  2. Проверьте файлы appsettings.json и appsettings.Development.json. Убедитесь, что там лежат только примеры (заглушки), а не реальные чувствительные данные (особенно в Connection Strings и JWT Key).
  3. Важно: Чтобы случайно не отправить локальные пароли в репозиторий при тестировании, добавьте ваши конфигурационные файлы с реальными данными (например, appsettings.Development.json или сам appsettings.json, если вы вписываете пароли прямо туда) в .gitignore. В репозитории должен остаться только файл-шаблон с примерами.
  4. Убедитесь, что в .gitignore также добавлена строка .env. Ваш локальный файл с паролями никогда не должен попасть в Git.

ШАГ 2: СОЗДАНИЕ СЕКРЕТОВ В GITHUB

Теперь нам нужно передать наши пароли самому GitHub, чтобы он мог использовать их при запуске автоматических задач (Actions).

  1. Откройте ваш репозиторий на сайте GitHub.
  2. Перейдите во вкладку Settings (Настройки) в верхнем меню репозитория.
  3. В левом боковом меню найдите раздел Security, раскройте пункт Secrets and variables и нажмите Actions.
  4. Нажмите зеленую кнопку New repository secret.
  5. Создайте секрет: в поле Name введите DB_PASSWORD, а в поле Secret — ваш реальный пароль от базы данных. Нажмите Add secret.
  6. Повторите процесс для других важных данных, например: JWT_SECRET_KEY, DB_USER.

Что гуглить: How to create encrypted secrets GitHub Actions.

ШАГ 3: ИСПОЛЬЗОВАНИЕ СЕКРЕТОВ В ПАЙПЛАЙНЕ (GITHUB ACTIONS)

Секреты созданы, но пайплайн о них не знает. Нам нужно явно передать их в шаги сборки или тестирования.

  1. Откройте файл вашего пайплайна (обычно это .github/workflows/main.yml).
  2. Найдите задачу (job), которой нужен доступ к базе данных или секретам (например, шаг с dotnet test).
  3. Внутри шага (step) добавьте блок env: и передайте секрет, используя специальный синтаксис GitHub: ${{ secrets.ИМЯ_СЕКРЕТА }}.

Пример:

steps:
  - name: Run Tests
    run: dotnet test
    env:
      JWT_SECRET: ${{ secrets.JWT_SECRET_KEY }}

ШАГ 4: ПЕРЕДАЧА СЕКРЕТОВ В DOCKER COMPOSE

Если в вашем пайплайне вы поднимаете инфраструктуру через docker compose up (например, для интеграционных тестов), вам не нужно физически создавать файл .env. Docker Compose автоматически подхватывает переменные из окружения системы (environment variables), в которой он запускается.

  1. Найдите в файле пайплайна шаг, где вы запускаете docker compose.
  2. Просто добавьте к этому шагу блок env: и замапьте (свяжите) ваши GitHub Secrets с именами переменных, которые ожидает docker-compose.yml.

Пример передачи переменных в Compose:

steps:
  - name: Run Docker Compose
    run: docker compose up -d
    env:
      DB_USER: ${{ secrets.DB_USER }}
      DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
      DB_NAME: ${{ secrets.DB_NAME }}
Как это работает: Когда GitHub Actions доходит до этого шага, он распаковывает секреты и кладет их в среду выполнения (OS environment) на время выполнения команды docker compose up. Compose видит в своем конфиге ${DB_PASSWORD}, заглядывает в среду выполнения, находит там пароль и успешно передает его контейнеру. Никаких временных файлов на диске не создается, что намного безопаснее!

ШАГ 5: ПРОВЕРКА И ЛОГИРОВАНИЕ

Пора проверить, всё ли мы сделали правильно и надежно ли GitHub скрывает наши данные.

  1. Закоммитьте изменения в конфигурационных файлах и пайплайне, и сделайте пуш в репозиторий.
  2. Откройте вкладку Actions в вашем репозитории на GitHub.
  3. Нажмите на запущенный процесс и перейдите к логам выполнения задач.
  4. Убедитесь, что база данных поднимается и тесты проходят успешно (переменные считываются корректно).
  5. Проверка маскировки: GitHub автоматически распознает использование секретов и заменяет их в логах на звездочки (***). Убедитесь, что в ваших логах нет открытых паролей!
ПРОМЕЖУТОЧНАЯ ПРОВЕРКА: Попробуйте специально изменить пароль в GitHub Secrets на неверный и перезапустить пайплайн. Ваши тесты или запуск базы данных должны упасть с ошибкой авторизации (Access Denied / Connection Refused). Если этого не произошло — значит, ваше приложение всё ещё читает пароль откуда-то из кода (захардкожен). Вернитесь к Шагу 1!
