ГАЙД ПО МОДУЛЮ М5: Мониторинг, логи и трассировка

Лабораторная работа №4: Observability для TodoApp

Цель работы: собрать для TodoApp полноценный observability-стенд, в котором метрики идут в Prometheus, логи попадают в Loki через Promtail, а трейсы отправляются в Tempo. Поверх этих источников будет работать Grafana, где вы увидите все три сигнала в одном интерфейсе.

ЗАЧЕМ НАМ ТРИ РАЗНЫХ ТИПА НАБЛЮДЕНИЯ? Метрики отвечают на вопрос "что деградирует и насколько быстро". Логи помогают понять "что именно произошло". Трейсы показывают "как запрос прошел через приложение по шагам". Grafana не заменяет эти системы: она только удобно собирает данные из специализированных источников.

ШАГ 1: СОБЕРИТЕ КАРТУ СТЕКА ПЕРЕД НАСТРОЙКОЙ

Сначала нужно понять роли компонентов. Если пропустить этот шаг, дальше легко начать копировать конфигурации вслепую и потерять смысл каждого сервиса.

Вопросы перед действием Почему Grafana не заменяет Prometheus, Loki и Tempo? Почему Loki сам по себе не умеет "забирать" логи из контейнеров без Promtail? Почему запущенный Tempo еще не означает, что в нем появятся трейсы?

Конкретное действие: перед правками составьте для себя короткую карту: кто собирает, кто хранит, кто визуализирует. Зафиксируйте минимум по одной функции на каждый сервис.

db         -> PostgreSQL с данными приложения
backend    -> ASP.NET Core API TodoApp
prometheus -> забирает метрики у backend по /metrics
loki       -> хранит логи
promtail   -> читает docker logs и отправляет их в Loki
tempo      -> принимает и хранит трейсы
grafana    -> показывает метрики, логи и трейсы в одном UI
Как проверить результат Вы должны уметь устно объяснить путь каждого сигнала: метрики идут напрямую из приложения в Prometheus, логи идут из stdout контейнера через Promtail в Loki, трейсы идут из приложения по OTLP в Tempo.
Типичная ошибка Считать, что Grafana "собирает" телеметрию сама. Нет: без корректно настроенных источников данных в Grafana просто будет красивый, но пустой интерфейс.

ШАГ 2: РАСШИРЬТЕ DOCKER COMPOSE ДО ПОЛНОГО OBSERVABILITY-СТЕНДА

Теперь нужно превратить ваш текущий compose-файл из набора db + backend в единый стенд наблюдаемости, который можно поднять одной командой.

Вопросы перед действием Какие сервисы должны стартовать вместе с приложением? Какие порты нужно открыть на хосте для проверки через браузер? К каким сервисам приложение должно обращаться по именам Docker-сервисов, а не через localhost?

Конкретное действие: обновите docker-compose.yml, оставьте существующие db и backend, затем добавьте prometheus, loki, promtail, tempo и grafana. Используйте стабильные pinned image tags и смонтируйте конфиги из репозитория.

services:
  db:
    image: postgres:16-alpine

  backend:
    build: .
    ports:
      - "5000:8080"
    environment:
      - OpenTelemetry__ServiceName=TodoApp.Web
      - OpenTelemetry__Otlp__Endpoint=http://tempo:4317

  prometheus:
    image: prom/prometheus:v2.54.1
    ports:
      - "9090:9090"

  loki:
    image: grafana/loki:3.1.1
    ports:
      - "3100:3100"

  promtail:
    image: grafana/promtail:3.1.1

  tempo:
    image: grafana/tempo:2.6.1
    ports:
      - "3200:3200"
      - "4317:4317"

  grafana:
    image: grafana/grafana-oss:11.1.4
    ports:
      - "3000:3000"
Как проверить результат В compose-файле должны появиться все семь сервисов: db, backend, prometheus, loki, promtail, tempo, grafana. Убедитесь, что backend отправляет трейсы в tempo:4317, а не в localhost:4317 внутри контейнера.
Типичная ошибка Использовать localhost для связи контейнеров между собой. Внутри Docker Compose localhost указывает на текущий контейнер, а не на соседний сервис.

ШАГ 3: ПОДГОТОВЬТЕ КОНФИГИ ДЛЯ PROMETHEUS, LOKI, PROMTAIL, TEMPO И GRAFANA

Сервисы observability лучше настраивать отдельными файлами в репозитории. Так конфигурация будет воспроизводимой, проверяемой и одинаковой у всей команды.

Вопросы перед действием Как Prometheus поймет, откуда забирать метрики? Как Promtail свяжет контейнер Docker с файлом логов? Почему datasource provisioning в Grafana удобнее ручного добавления через UI?

Конкретное действие: создайте дерево observability/ и добавьте конфиги для каждого сервиса. Важно, чтобы они ссылались на имена docker-сервисов: backend, loki, prometheus, tempo.

observability/
  prometheus/prometheus.yml
  loki/loki-config.yml
  promtail/promtail-config.yml
  tempo/tempo.yml
  grafana/provisioning/datasources/datasources.yml
# prometheus.yml
scrape_configs:
  - job_name: todoapp-backend
    metrics_path: /metrics
    static_configs:
      - targets: ["backend:8080"]

# promtail-config.yml
clients:
  - url: http://loki:3100/loki/api/v1/push

# datasources.yml
datasources:
  - name: Prometheus
    url: http://prometheus:9090
  - name: Loki
    url: http://loki:3100
  - name: Tempo
    url: http://tempo:3200
Как проверить результат В prometheus.yml должен быть target backend:8080 и путь /metrics. В Grafana datasource-файл должен описывать три источника данных, чтобы после старта они появились автоматически без ручной настройки.
Типичная ошибка Создать конфиг-файлы, но забыть смонтировать их в docker-compose.yml. В результате контейнер поднимается с дефолтной конфигурацией, и вы отлаживаете "не тот" стенд.

ШАГ 4: ПОДГОТОВЬТЕ TODOAPP К МЕТРИКАМ И ТРЕЙСАМ

Prometheus не создает метрики магически, а Tempo не получает трейсы сам по себе. Приложение должно быть явно инструментировано.

Вопросы перед действием Какие NuGet-пакеты нужны для OpenTelemetry? Какие данные можно получить автоматически из ASP.NET Core? Почему для метрик нужен endpoint /metrics, а для трейсов нужен OTLP exporter?

Конкретное действие: добавьте OpenTelemetry-пакеты в проект, настройте общий resource с именем сервиса, включите ASP.NET Core и HttpClient instrumentation, откройте endpoint /metrics и настройте отправку трейсов в Tempo.

builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource.AddService(serviceName))
    .WithMetrics(metrics => metrics
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()
        .AddPrometheusExporter())
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddOtlpExporter(options =>
        {
            options.Endpoint = new Uri(otlpEndpoint);
        }));

app.MapPrometheusScrapingEndpoint("/metrics");
Как проверить результат После сборки приложения у вас должен существовать маршрут /metrics. В конфигурации приложения должны быть параметры вроде OpenTelemetry:ServiceName и OpenTelemetry:Otlp:Endpoint. Serilog при этом должен остаться включенным, потому что именно stdout контейнера будет источником логов для Promtail.
Типичная ошибка Удалить существующее логирование, думая, что OpenTelemetry полностью его заменяет. В этой лабораторной логи остаются в stdout, а Promtail уже читает их и отправляет в Loki.

ШАГ 5: ПОДНИМИТЕ СТЕК И ПРОВЕРЬТЕ, ЧТО ВСЕ СЕРВИСЫ ЖИВЫ

После конфигурирования нужно проверить не только факт запуска, но и то, что сервисы поднялись без скрытых ошибок конфигурации.

Вопросы перед действием Какие контейнеры должны быть в состоянии Up? Какие URL вы будете открывать первыми для быстрой проверки? Что делать, если один контейнер постоянно перезапускается?

Конкретное действие: из корня проекта выполните полную пересборку и запуск стенда.

docker compose up -d --build
docker ps

После запуска откройте:

  • http://localhost:5000/swagger для API;
  • http://localhost:3000 для Grafana;
  • http://localhost:9090/targets для Prometheus;
  • http://localhost:3200 для Tempo.
Как проверить результат В выводе docker ps должны быть видны контейнеры todoapp-db, todoapp-backend, todoapp-prometheus, todoapp-loki, todoapp-promtail, todoapp-tempo и todoapp-grafana. В Prometheus target для backend должен перейти в состояние UP.
Типичная ошибка Проверять только наличие контейнера в списке, но не смотреть его логи. Контейнер может существовать и одновременно бесконечно падать из-за неверного пути к конфигу или неправильного порта.

ШАГ 6: СОЗДАЙТЕ ТЕСТОВУЮ НАГРУЗКУ, ЧТОБЫ ПОЯВИЛИСЬ ДАННЫЕ

Пустая система наблюдаемости почти всегда выглядит как "ничего не работает". На самом деле ей просто не хватает событий. Нужно создать нагрузку вручную.

Вопросы перед действием Какие запросы лучше отправить, чтобы появились и успешные, и ошибочные сценарии? Почему после старта системы данные не появляются мгновенно во всех источниках?

Конкретное действие: откройте Swagger и выполните несколько запросов подряд. Полезно сделать комбинацию из чтения списка задач, создания задачи и одного невалидного запроса, чтобы в логах и трейсах были разные сценарии.

Пример последовательности:
1. GET /api/todos
2. POST /api/todos с валидным телом
3. GET /api/todos
4. POST /api/todos с некорректным телом или без токена
5. Повторить 2-3 раза
Как проверить результат После серии запросов у backend должны обновиться счетчики HTTP-запросов, в Loki должны появиться строки логов, а в Tempo должны появиться новые trace/span записи. Если данных нет, сначала убедитесь, что вы действительно отправили несколько HTTP-запросов после старта контейнеров.
Типичная ошибка Открыть только Swagger UI и не выполнить ни одного endpoint. Само открытие страницы даст слишком мало данных, чтобы уверенно проверить весь pipeline.

ШАГ 7: ПРОВЕРЬТЕ МЕТРИКИ В PROMETHEUS

Метрики обычно дают первый сигнал о проблеме. Здесь ваша цель — убедиться, что приложение действительно публикует метрики, а Prometheus их реально забирает.

Вопросы перед действием Почему target может быть DOWN, даже если backend отвечает в браузере? Что означает путь /metrics и кто его обслуживает: ваш контроллер или middleware/exporter?

Конкретное действие: зайдите в Prometheus, откройте Status -> Targets, затем выполните простой запрос в интерфейсе Prometheus, например по числу HTTP-запросов.

http_server_request_duration_seconds_count

или

http_server_active_requests
Как проверить результат Target todoapp-backend должен быть UP. Метрики должны возвращать значения, а не пустой список. Если открыть http://localhost:5000/metrics напрямую, вы должны увидеть текстовый поток метрик.
Типичная ошибка Ожидать пользовательские бизнес-метрики, хотя вы настроили только базовую автоматическую instrumentation. В этой работе достаточно системных и HTTP-метрик, которые появляются автоматически.

ШАГ 8: ПРОВЕРЬТЕ ЛОГИ В LOKI И GRAFANA

Логи нужны, чтобы быстро увидеть конкретные сообщения приложения и контекст ошибки. Здесь мы проверяем полный путь: контейнер -> Promtail -> Loki -> Grafana.

Вопросы перед действием Почему Loki не читает stdout контейнеров напрямую? Какие label-поля помогут отличить backend от остальных контейнеров? Как понять, что проблема именно в Promtail, а не в Loki?

Конкретное действие: откройте Grafana, перейдите в Explore, выберите datasource Loki и найдите логи backend по label контейнера или compose-сервиса.

{container="todoapp-backend"}

или

{compose_service="backend"}
Как проверить результат В Grafana должны появиться строки логов от ASP.NET Core/Serilog после ваших запросов. Если видны логи только от инфраструктурных контейнеров, значит backend либо не пишет в stdout, либо Promtail не собирает нужный контейнер.
Типичная ошибка Искать логи сразу по слишком узкому запросу и решить, что логов нет. Сначала попробуйте более широкий фильтр по контейнеру, а уже потом сужайте поиск.

ШАГ 9: ПРОВЕРЬТЕ ТРЕЙСЫ В TEMPO И GRAFANA

Трейсы особенно полезны, когда нужно восстановить путь запроса и понять, где именно возникла задержка или ошибка.

Вопросы перед действием Почему поднятый Tempo может оставаться пустым? Какие действия в приложении создают новые spans автоматически? Почему после первого запуска иногда нужно подождать несколько секунд, прежде чем trace станет видимым?

Конкретное действие: в Grafana откройте datasource Tempo через Explore, выберите сервис TodoApp.Web и найдите недавние traces после серии запросов в Swagger.

Service name: TodoApp.Web
Lookback: Last 15 minutes
Query type: Search
Как проверить результат Вы должны увидеть хотя бы один trace со span-ами HTTP-запроса. При открытии trace должны быть видны длительность, статус и дочерние операции. Если trace не появляется, проверьте endpoint OTLP в backend и receiver OTLP в Tempo.
Типичная ошибка Смотреть только веб-страницу Tempo и не проверять настройку экспортера в самом приложении. Tempo может быть полностью исправен, но пуст, если backend никуда не отправляет трейсы.

ШАГ 10: СОБЕРИТЕ ВСЕ ТРИ СИГНАЛА В GRAFANA

Последний шаг нужен, чтобы увидеть observability как единую систему, а не как три несвязанных проверки.

Вопросы перед действием С какого сигнала вы начнете расследование инцидента: с метрик, логов или трейсов? Почему это зависит от симптома? Как связать сигнал "высокая задержка" с конкретным trace и затем с логами?

Конкретное действие: проверьте в Grafana, что все три datasource доступны, затем сравните результаты: сначала найдите всплеск или изменение в метриках, после этого откройте логи backend, а затем trace недавнего запроса.

Порядок ручной проверки:
1. Prometheus datasource -> метрики backend
2. Loki datasource -> логи backend
3. Tempo datasource -> traces сервиса TodoApp.Web
4. Сопоставьте время события во всех трех сигналах
Как проверить результат В разделе Connections или Data sources Grafana все три источника должны быть в статусе working. Вы должны уметь показать преподавателю один и тот же период времени через метрики, логи и trace.
Типичная ошибка Проверить каждый инструмент отдельно, но не попытаться связать их по времени и по сервису. Настоящая ценность observability появляется именно в совместном использовании сигналов.

ЧАСТЫЕ ОШИБКИ И ДИАГНОСТИКА

  • Prometheus target DOWN: проверьте путь /metrics, порт backend и имя target backend:8080.
  • Нет логов в Loki: проверьте, что Promtail смонтировал /var/lib/docker/containers и /var/run/docker.sock, а backend действительно пишет в stdout.
  • Нет traces в Tempo: проверьте OpenTelemetry__Otlp__Endpoint=http://tempo:4317 и наличие OTLP receiver в tempo.yml.
  • Grafana пустая после старта: убедитесь, что provisioning-файл datasource смонтирован в правильную директорию.
  • Данные появились не сразу: повторите несколько HTTP-запросов и дайте системе 10-30 секунд на сбор и индексацию.
