ГАЙД ПО МОДУЛЮ М3: GitHub Actions для TodoApp

CI (Continuous Integration) — это сердце DevOps. Это процесс, который автоматически проверяет ваш код на ошибки ПРЕЖДЕ, чем он попадет в продакшн.

ЗАЧЕМ ЭТО НУЖНО БИЗНЕСУ? Автоматизация тестов в CI гарантирует, что "младший разработчик Петя" не сломает проект в пятницу вечером перед релизом. Конвейер (Workflow) просто не пропустит его код дальше, если хоть один тест завершится с ошибкой.

ШАГ 1: СОЗДАНИЕ ФАЙЛА .github/workflows/ci.yml

Это главный конфигурационный файл для GitHub Actions. GitHub ищет его строго в папке .github/workflows/ вашего репозитория. Если он там есть — GitHub автоматически запускает Workflow (конвейер) при событиях, которые вы укажете (например, при пуше или pull request'е).

Что мы описываем в файле:

  1. Triggers (Триггеры): Указываем on: [push, pull_request], чтобы пайплайн запускался при любых пушах и создании PR.
  2. Jobs (Задачи): Обычно в .NET проектах мы делаем одну задачу build-and-test, которая выполняется на ubuntu-latest.
  3. Steps (Шаги): Внутри задачи мы прописываем шаги:
    • actions/checkout — скачивает ваш код на сервер (runner).
    • actions/setup-dotnet — устанавливает нужную версию .NET SDK.
    • dotnet restore, dotnet build и dotnet test — собирают проект и запускают тесты.
  4. Cache (Кэш): GitHub Actions умеет кэшировать NuGet-пакеты автоматически с помощью экшена `setup-dotnet`, что ускоряет сборку в несколько раз.

ШАГ 2: НАСТРОЙКА ПРАВИЛ ЗАЩИТЫ ВЕТКИ MAIN (Branch Protection Rules)

Теперь нам нужно запретить пушить код напрямую в ветку main и сделать так, чтобы код мог попасть туда только через Pull Request и только если тесты прошли успешно.

  1. Зайдите в ваш репозиторий на GitHub, перейдите во вкладку Settings.
  2. Слева в меню выберите Branches и нажмите Add branch ruleset (или Add branch protection rule).
  3. В поле Branch name pattern введите main.
  4. Поставьте галочку Require a pull request before merging (Запрещает прямой пуш, требует PR).
  5. Поставьте галочку Require status checks to pass before merging. В появившемся поиске найдите и выберите имя вашей джобы (например, build-and-test). Это запретит апрувить и мержить PR, если CI упал.
  6. Сохраните изменения (кнопка Create или Save changes).

ШАГ 3: ПРАКТИЧЕСКОЕ ЗАДАНИЕ (УПАВШИЙ ТЕСТ И PULL REQUEST)

Теперь проверим, как наша защита работает на практике. Мы создадим новую ветку, напишем заведомо неправильный тест, создадим Pull Request (который GitHub заблокирует), а затем исправим его.

  1. Создайте новую ветку: 
    git checkout -b feature/auth-tests
  2. Напишите неправильный тест. Например, тест, который отправляет пустой пароль, но ожидает, что сервер вернет статус OK: 
    [Fact]
public async Task Register_ReturnsOk_WhenPasswordIsEmpty()
{
    // Отправляем запрос с пустым паролем
    var response = await _client.PostAsJsonAsync("/api/v1/auth/register",
        new RegisterRequest("test@example.com", ""));
    
    // НЕПРАВИЛЬНО: ожидаем OK (200), хотя сервер должен выдать ошибку
    response.StatusCode.Should().Be(HttpStatusCode.OK);
}
  3. Отправьте код и создайте Pull Request: 
    git add .
git commit -m "test: add bad register test"
git push origin feature/auth-tests
    Зайдите на GitHub и создайте Pull Request из feature/auth-tests в main.













  4. Убедитесь, что CI упал. Зайдите в ваш PR. Вы увидите красный крестик — тесты не прошли. Кнопка Merge pull request будет заблокирована правилом, которое мы создали на Шаге 2.
  5. Исправьте тест. В коде поменяйте ожидаемый статус на правильный (например, BadRequest): 
    [Fact]
public async Task Register_ReturnsBadRequest_WhenPasswordIsEmpty()
{
    var response = await _client.PostAsJsonAsync(
        "/api/v1/auth/register",
        new RegisterRequest("test@example.com", ""));
    
    // ПРАВИЛЬНО: ожидаем ошибку (400 BadRequest)
    response.StatusCode.Should().Be(HttpStatusCode.BadRequest);
}
  6. Отправьте исправление: 
    git add .
git commit -m "fix: assert correct error status for empty password"
git push origin feature/auth-tests
  7. Вернитесь в Pull Request на GitHub. Дождитесь, пока CI пройдет (загорится зеленая галочка). Кнопка Merge pull request станет доступной. Нажмите её!

КАК ПРОВЕРИТЬ РАБОТУ И ЧТО СДАВАТЬ?

  1. Вы можете следить за выполнением вашего CI в реальном времени. В репозитории на GitHub перейдите на вкладку Actions.
  2. Кликните по последнему запущенному Workflow и посмотрите логи выполнения шагов (checkout, build, test).
  3. ДЛЯ СДАЧИ РАБОТЫ: Создайте текстовый файл, вставьте в него ссылку на ваш Pull Request (в котором видно историю: сначала упавший коммит, затем исправленный коммит, и успешный Merge). Отправьте этот файл в качестве ответа на задание.

🔥 ЧАСТЫЕ ВОПРОСЫ И ОШИБКИ

  • 🔴 Workflow вообще не запустился
    Причина: Файл лежит не по тому пути. Убедитесь, что он находится строго в .github/workflows/ci.yml (папка начинается с точки!).

  • 🔴 Тесты локально работают, а в GitHub Actions падают
    Причина: Часто бывает связано с путями к файлам (Linux в GitHub Actions чувствителен к регистру в отличие от Windows) или с отсутствием переменных окружения/конфигов, которые локально у вас есть, а в репозиторий не добавлены (например, appsettings.json или строки подключения).
