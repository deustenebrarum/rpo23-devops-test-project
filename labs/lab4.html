ГАЙД ПО МОДУЛЮ М4: Continuous Deployment (CD) через GitHub Actions

Цель работы: Настроить автоматическое развертывание (деплой) приложения. Теперь, когда вы делаете git push в ветку main, GitHub должен не только проверить код (CI), но и автоматически обновить работающее приложение на вашем "боевом" сервере с помощью Docker Compose.

КАК МЫ БУДЕМ ЭТО ДЕЛАТЬ НА ЛОКАЛЬНОМ ПК? В реальной жизни GitHub подключается к удаленному серверу (VPS) по SSH. Но у вашего домашнего компьютера (Windows/WSL) нет публичного IP-адреса, поэтому GitHub не может к нему "постучаться". Решение: мы установим на ваш ПК Self-Hosted Runner. Это программа-шпион, которая сама постоянно спрашивает GitHub: "Для меня есть работа?". Как только появляется новый код, раннер скачивает его и выполняет команды прямо на вашем компьютере. Ваша машина станет "боевым сервером".

ШАГ 1: ПОДГОТОВКА "СЕРВЕРА" (Windows/WSL)

Перед тем как настраивать автоматику, нужно убедиться, что окружение готово принимать приложение.

  1. Откройте терминал (Ubuntu в WSL или PowerShell, в зависимости от того, где у вас установлен Docker).
  2. Убедитесь, что Docker запущен: выполните команду docker ps. Если ошибок нет — сервер готов.
  3. Остановите и удалите ваши старые локальные контейнеры проекта (если они запущены), чтобы освободить порты: docker compose down (выполнять в папке проекта).

ШАГ 2: НАСТРОЙКА SELF-HOSTED RUNNER

Сейчас мы привяжем ваш компьютер к репозиторию GitHub в качестве агента для выполнения пайплайнов.

  1. Откройте ваш репозиторий на GitHub.
  2. Перейдите: Settings -> Actions -> Runners.
  3. Нажмите зеленую кнопку New self-hosted runner.
  4. Выберите операционную систему вашего "сервера" (Windows или Linux, если используете чистый WSL для запуска).
  5. GitHub покажет вам набор команд (в блоках Download и Configure). Откройте терминал на вашем ПК, создайте новую пустую папку (например, mkdir actions-runner && cd actions-runner) и по очереди скопируйте и выполните все предложенные команды.
  6. При конфигурации (команда ./config.sh или config.cmd) у вас спросят имя раннера и метки (tags). Можете просто нажимать Enter, оставив всё по умолчанию.
  7. Выполните последнюю команду: ./run.sh (или run.cmd). В терминале появится надпись Connected to GitHub и Listening for Jobs. Не закрывайте этот терминал! Ваш сервер готов к приему команд.
Как проверить результат: Вернитесь на страницу Runners в GitHub. Вы должны увидеть ваш компьютер в списке со статусом Idle (Ожидает).

ШАГ 3: СОЗДАНИЕ CD ПАЙПЛАЙНА

Теперь нужно написать инструкцию, которую GitHub передаст вашему компьютеру при обновлении кода.

  1. В вашем проекте создайте новый файл .github/workflows/cd.yml (отдельно от ci.yml).
  2. Укажите триггер запуска: пайплайн должен запускаться только при пуше в ветку main.
  3. Создайте job с именем deploy.
  4. КРИТИЧЕСКИ ВАЖНО: Укажите runs-on: self-hosted. Это скажет GitHub отправить задачу не на свои облачные сервера, а на ваш запущенный терминал.

Каркас вашего файла:

name: Continuous Deployment

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: self-hosted
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        
      # Дальше напишем шаги деплоя...

ШАГ 4: ШАГИ РАЗВЕРТЫВАНИЯ И СЕКРЕТЫ

Добавьте шаги (steps) в ваш файл cd.yml для запуска Docker Compose. Так как это CD, нам нужно передать секреты прямо на сервер.

  1. Шаг генерации .env файла: В отличие от тестов, на боевом сервере контейнеры работают постоянно. Если сервер перезагрузится, Docker должен запустить базу данных с правильным паролем. Поэтому мы физически создадим файл .env в рабочей папке раннера перед запуском.
  2. Используйте команду echo для записи секретов в файл (как мы делали в предыдущем модуле).
  3. Шаг перезапуска Compose: Напишите команду, которая остановит старые контейнеры, пересоберет образ с новым кодом и запустит в фоновом режиме. (docker compose down, затем docker compose up -d --build).
      - name: Create Environment File
        run: |
          echo "DB_USER=${{ secrets.DB_USER }}" > .env
          echo "DB_PASSWORD=${{ secrets.DB_PASSWORD }}" >> .env
          echo "DB_NAME=${{ secrets.DB_NAME }}" >> .env

      - name: Deploy application
        run: |
          docker compose down
          docker compose up -d --build

Что гуглить: GitHub Actions self-hosted docker compose deploy.

ШАГ 5: ПОЛНАЯ ПРОВЕРКА ЦИКЛА (МАГИЯ DEVOPS)

Пора проверить весь процесс от написания кода до его появления на сервере.

  1. Убедитесь, что терминал с вашим раннером всё ещё открыт и ждет задач (Listening for jobs).
  2. Откройте код вашего проекта (например, в контроллере или HTML файле) и сделайте видимое изменение. Измените заголовок или текст.
  3. Сделайте коммит и пуш в ветку main.
  4. Откройте GitHub -> Actions. Вы увидите, как запустился ваш CD пайплайн . Посмотрите в ваш открытый терминал с раннером — там начнут бежать строки скачивания и сборки Docker!
  5. Дождитесь зеленой галочки успешного выполнения в интерфейсе GitHub.
  6. Откройте браузер и перейдите по адресу вашего приложения (например, http://localhost:8080/swagger). Вы должны увидеть ваши новые изменения. Приложение обновилось полностью автоматически!
ЧТО ПРОИЗОШЛО? Вы только что построили настоящий CI/CD конвейер. Разработчик просто пишет код и делает push в ветку main. GitHub сам прячет секреты, раннер сам получает сигнал и скачивает обновления, а Docker сам пересобирает и перезапускает приложение. Добро пожаловать в DevOps!
